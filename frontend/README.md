# PlantSage Frontend

This is the restored PlantSage 1.0 Flutter frontend, adopted as the latest
frontend development baseline on 2026-11-15 after user testing on Android.
The FastAPI backend remains at the repository root and is unchanged by this addition.

## Recovery

The 18 application Dart files were extracted as embedded source text from the
original installed debug APK, not reconstructed from screenshots. They include
the original home dashboard, garden, care calendar, wishlist, diagnosis, results,
onboarding, settings, and API services.

The original dependency manifests and Android project were not recovered. This
baseline uses the existing replacement project's build configuration and lockfile.
One calendar dropdown argument was adapted from `initialValue` to `value` for the
installed Flutter 3.32.4 / Dart 3.8.1 SDK. No SDK or dependency upgrade was performed.

## Android Setup

Install Flutter 3.32.4, Dart 3.8.1, the Android SDK, and JDK 17. Start in `frontend/`.
Create an untracked `android/local.properties` using your own installation paths:

```properties
sdk.dir=/path/to/Android/Sdk
flutter.sdk=/path/to/flutter
```

The Gradle wrapper launchers and JAR are generated by Flutter tooling and are not
versioned, following the Android ignore rules. After configuring the SDK paths:

```shell
flutter pub get
flutter test --no-pub
flutter build apk --release --no-pub
```

Use the committed lockfile; do not run `flutter pub upgrade` for routine builds.
An offline build can use `flutter pub get --offline` when all dependencies are cached.
If the test runner's localhost WebSocket is intercepted by a proxy, configure
`NO_PROXY=localhost,127.0.0.1,::1` for the test process.

## Phone Safety

- Android application ID: `com.plantsage.plantstage`.
- Launcher label: `PlantSage 1.0 Restored`; version name: `1.0`.
- Do not use `com.myplants.myplants_app`: it belongs to the preserved original app.
- Release builds currently use a local debug signing key for development only.
  Configure private production signing separately before publishing to a store.
- Backend actions can affect shared production data even when the Android apps
  are installed separately. Avoid reset/delete operations during smoke testing.

## Repository Deployment

Railway services deploy the backend from `master` at the repository root. This
frontend addition is published on `restore/plantsage-frontend-v1` to avoid triggering
those production deployments. Configure backend-only watch paths before merging
frontend-only changes into `master`, or explicitly plan for the resulting backend
redeploy. Do not change the Railway root directory to `frontend/`.

Secrets, signing keys, APKs, caches, local SDK paths, and recovery backups must not
be committed. Keep offline backups of signing keys separately from this repository.
